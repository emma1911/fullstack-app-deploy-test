# Nexus Repository Installation

## Why Do We Use Nexus?

Nexus is a repository manager that helps us store and manage project artifacts (such as `.jar` files).

### Main Reason for using Nexus:

When we update our code on GitHub and rebuild the project, a new version of the `.jar` file is generated.

Nexus allows us to store these `.jar` files safely. The previous `.jar` file continues to run without interruption. Once the new `.jar` file is successfully built, it replaces the old one.

This process helps avoid downtime and ensures the application remains available during updates.

## To perform a clean installation of Nexus, we followed these steps:

1. We pull the latest Sonatype Nexus Repository Docker image using the following command: 

```bash
   sudo docker pull sonatype/nexus3:latest
```
   sonatype is the Docker Hub organization that publishes the Nexus image.
   nexus3 is the image name.
   latest is the latest available version tag.

2. We create the ~/nexus-data folder because it will be used later as a Docker volume to store all Nexus data permanently, such as:

    repositories
    uploaded artifacts
    configuration
    users and passwords
    logs

```bash
    mkdir -p ~/nexus-data
```
3. We change the permissions of the ~/nexus-data folder so the Docker container can read from and write to it without permission issues.

```bash
    sudo chmod -R 777 ~/nexus-data
```
    chmod changes folder permissions.
    -R applies the permissions recursively to all files and subfolders.
    777 gives full read, write, and execute permissions to everyone.

4. we create and start the Docker container for nexus.
   with the following command:

```bash
   sudo docker run -d \
    --name nexus \
    -p 8081:8081 \
    -v ~/nexus-data:/nexus-data \
    sonatype/nexus3
```
sudo docker run : creates and starts a new container from an image.
-d : is to runs the container in the backgroud.
--name nexus : assigns the container the name nexus for easier management.
-p 8081:8081 : maps port 8081 inside the container to port 8081 on the host machine with this it allow us access via browser. 
-v ~/nexus-data:/nexus-data : is to give the container a volume that saves the data inside the host machine, even if the container is removed.
sonatype/nexus3 : the Docker image used to run Nexus.

After that we can just run the container with :

```bash
    sudo docker start nexus
    sudo docker stop nexus
    sudo docker logs nexus
```
## Opening Firewall Port for Nexus

To access Nexus from the web browser, we need to allow traffic through the firewall on port 8081.

We added a new firewall rule using the following command:

```bash
sudo ufw allow 8081
```

Explanation: This command opens port 8081 so that we can connect to the Nexus web interface from our browser.

## Getting the Initial Admin Password for Nexus

After opening Nexus in the browser, we need to retrieve the initial administrator password.

We navigated to the following directory then displayed the content of the `admin.password` file using the command :

```bash
cat nexus-data/admin.password
```
This file contains the temporary admin password generated by Nexus.
We use this password to log in to the Nexus web interface. After logging in, Nexus will ask us to change this password immediately, after updating the password Nexus automatically deletes the admin.password file for security reasons.

## Uploading a JAR File to Nexus

To upload our `.jar` file into Nexus, we follow these steps:

1. Open the Nexus web interface.
2. Go to the repository where we want to upload the file.
3. Click on Browse.
4. Select `maven-releases`
5. Click on Upload Component.

Then we select and upload our `.jar` file through the browser.

## Repository Types in Nexus

Inside Nexus, we have several repositories. Each repository has its own purpose and its own unique URL.

In our project, we mainly use only two of them: maven-releases and maven-snapshots.

1. maven-central (Proxy Repository)

Role: It is a local copy of the official Maven Central repository.
Purpose: It downloads external libraries (like Spring Boot) from the internet once and saves them. This makes downloads faster and allows us to work even if the internet is slow or down.
URL: http://192.168.56.23:8081/repository/maven-central/

2. maven-public (Group Repository)

Role: It is a combined (group) repository.
Purpose: It gives one single access point. Instead of connecting to many repositories, you can connect only to maven-public, and it will automatically search in all other repositories (maven-central, maven-releases, and maven-snapshots).
URL: http://192.168.56.23:8081/repository/maven-public/

3. maven-releases (Hosted Repository)

Role: This is our private repository for stable and final versions.
Purpose: We store official, tested, and completed versions of our own projects here. These versions do not change.
URL: http://192.168.56.23:8081/repository/maven-releases/
We used in our project for final versions.

4. maven-snapshots (Hosted Repository)

Role: This is our private repository for development versions.
Purpose: We use it during active development. These versions change frequently (every time we update the code).
URL: http://192.168.56.23:8081/repository/maven-snapshots/
We used in our project for work-in-progress versions.

## How we use maven-releases and maven-snapshots in Our Project?

To connect our project to these repositories, we configured two important files: settings.xml and pom.xml.

1. settings.xml File

This file is used to store login information (username and password) for Nexus. 
Maven reads this file so it can connect securely to the repositories.

<servers>
    <server>
        <id>nexus-snapshots</id>
        <username>admin</username>
        <password>Emna19112002@</password>
    </server>
    <server>
        <id>nexus-releases</id>
        <username>admin</username>
        <password>Emna19112002@</password>
    </server>
</servers>

This file tells Maven When you need to connect to nexus-snapshots or nexus-releases, use these username and password.

2. pom.xml Configuration

In our project’s pom.xml file, we added the <distributionManagement> section. This tells Maven where to upload or deploy our project files.

<distributionManagement>
    <snapshotRepository>
        <id>nexus-snapshots</id>
        <url>http://192.168.56.23:8081/repository/maven-snapshots/</url>
    </snapshotRepository>
    <repository>
        <id>nexus-releases</id>
        <url>http://192.168.56.23:8081/repository/maven-releases/</url>
    </repository>
</distributionManagement>

If our project version ends with -SNAPSHOT (example: 1.0-SNAPSHOT), Maven will upload it to maven-snapshots.
If it is a final version (example: 1.0), Maven will upload it to maven-releases.

## Deploying using Jenkins

We created an automatic deployment stage in our Jenkins pipeline

stage('Deploy to Nexus') {
    steps {
        echo 'Publication sur Nexus...'
        dir('deployment-app-back') {                    
            sh 'mvn deploy -DskipTests -s ../settings.xml'   
        }
    }
}

## What does this stage?

This stage automatically uploads our Spring Boot application to Nexus. Here is the step-by-step process:

1. Jenkins goes into the project folder (deployment-app-back)
2. It runs mvn deploy command
3. Maven looks at the <version> in my pom.xml:
    If version = 1.0-SNAPSHOT ==> uploads to maven-snapshots
    If version = 1.0 ==> uploads to maven-releases
4. Maven uses the credentials from settings.xml to log in to Nexus.
5. The JAR file is uploaded to the correct repository.
